# meshvoice — Phase 0 mesh-voice simulator

A discrete-event network simulator for **Lyra voice over a Bluetooth LE mesh**. It exists to
de-risk the riskiest promise of the hybrid messenger (see [`../docs/03-voice-lyra-mesh.md`](../docs/03-voice-lyra-mesh.md))
with measured numbers instead of assumptions: how many concurrent calls a BLE link/cluster
sustains, how mouth-to-ear latency grows per hop, and how much adaptive bitrate buys.

Pure Python standard library (numpy optional, not required). No third-party repositories,
no network access, no credentials.

## Run

```bash
cd sim
python3 -m pytest -q          # network model
python3 run_sweep.py          # writes results/ and prints the tables
```

Perceptual quality (ViSQOL, DNSMOS, STOI) of real Lyra audio under the same mesh
losses is a separate harness: `python3 run_quality.py`. It needs the packages in
`requirements-quality.txt` and a local build of Lyra 1.3.2 (`quality/setup_lyra.sh`).
See [Voice quality](#voice-quality) below.

## What it models

- **Codec** (`codec.py`): Lyra v2 rates (3.2 / 6 / 9.2 kbps), 20 ms frames (calibratable),
  per-packet overhead, and frame batching that amortizes overhead.
- **Network** (`network.py`): a graph of nodes and directed BLE links. A link has an
  *effective application-layer capacity* (goodput after BLE link-layer overhead), a
  connection interval, and a residual error rate. Topologies: line, ring, star, grid,
  random-geometric (phones placed in a square, linked within radius).
- **Routing** (`routing.py`): fewest-hop (BFS) and lowest-expected-latency (Dijkstra over
  serialization + half a connection interval), with an optional hop limit.
- **Simulator** (`simulator.py`): every packet traverses its path hop by hop. Each directed
  link is a FIFO server: a packet waits for the next connection event (access latency),
  then queues behind earlier packets, then occupies the link for its serialization time.
  Losses come from (a) residual per-link error, (b) buffer overflow on a saturated link,
  (c) arriving after the jitter-buffer playout deadline. Global time-ordered event
  processing makes per-link FIFO queueing exact; a seeded RNG makes runs reproducible.
- **Metrics** (`metrics.py`): mouth-to-ear latency percentiles, loss broken down by cause,
  per-link utilization. Mouth-to-ear = packet build-up + encode + network + decode.
- **Scenarios** (`scenarios.py`): the shared-relay stress test, per-hop latency line, the
  random-geometric cluster, the adaptive-bitrate lever, and a breaking-point search (largest
  concurrent-call count meeting the QoS target: p95 ≤ 200 ms and loss ≤ 2%).

## Headline results (`results/summary.md`, regenerated by `run_sweep.py`)

- **Single-link capacity tracks the analytic bound.** Classic BLE (37.5 kbps usable) holds
  2 / 3 / 4 concurrent calls at 9.2 / 6 / 3.2 kbps; BLE 5 (250 kbps) holds 17 / 23 / 31.
  The clean-room cross-check (`test_scenarios.py`, no header overhead) reproduces the doc's
  napkin math *exactly*: **4 calls @ 9.2 kbps and 11 @ 3.2 kbps per 37.5 kbps link.**
- **Overhead matters more than expected for tiny frames.** A 23-byte 9.2 kbps frame plus a
  12-byte RTP-sized header is 35 bytes on the wire — so realistic capacity is ~2 calls, vs
  4 with no overhead. Header compression / frame batching recovers most of it; this is a
  concrete, high-leverage implementation lever.
- **Single-call latency permits more hops than first guessed.** At a 15 ms connection
  interval, per-hop cost is ~15 ms, so one call stays under the 200 ms budget out to ~7–10
  BLE hops. The real limit on mesh voice is therefore **per-link concurrent-call capacity
  and battery**, not single-call hop latency — a refinement of the original 2–3-hop estimate.
- **A realistic 24-node cluster** carries ~10 calls at 9.2 kbps / ~25 at 3.2 kbps on classic
  BLE, and ≥60 on BLE 5 (the search ceiling), at ~2–3 average hops.
- **Adaptive bitrate (9.2k → 3.2k under load) doubles** a classic-BLE relay from 2 to 4
  concurrent calls.

## Modeling assumptions & limitations (calibration targets for the Phase 4 on-device bench)

- Link capacity is *effective goodput*; BLE link-layer framing/ARQ is folded into that number
  plus a small residual error rate, rather than simulated at the packet-fragment level.
- One end-to-end jitter buffer per call (not per hop); no explicit RF collision/interference
  model beyond the residual error rate; no mobility.
- **No battery/CPU model** — Lyra decode cost under many simultaneous calls is a known open
  risk and must be measured on hardware, not inferred here.
- This simulator models *timing/capacity*, not audio quality — but `SimParams(trace=True)` exports a
  per-call packet-delivery trace that the [`voice/`](../voice) harness replays through the codec +
  jitter buffer + PLC to score how a call under these exact conditions actually *sounds*
  (`voice/tests/test_sim_bridge.py`).
- Default encode/decode delays and connection interval are nominal; the on-device bench
  recalibrates them and the model re-runs unchanged.

These are deliberately conservative where it matters; the simulator's job is to find the
*shape* of the limits and the load breakpoints, which it does and cross-checks against
closed-form capacity.

## Voice quality

`run_quality.py` pushes the committed 12 s clean-speech fixture through Lyra v2 at
3.2, 6, and 9.2 kbps, then through the mesh conditions in `quality/channel.py`
(residual packet loss, a tight jitter buffer, 3- and 5-hop paths, and a loaded
relay). The simulator's per-frame fate is the decoder's packet-loss pattern:
played frames are decoded, everything else is Lyra packet-loss concealment.
Jitter that the buffer absorbs does not warp the waveform.

Each waveform is scored with:

- **ViSQOL** speech mode (lattice MOS-LQO), against the clean fixture
- **DNSMOS P.835** overall / signal / background, a reference-free neural MOS
- **STOI**, after compensating Lyra's encode delay

`quality/thresholds.json` is the gate. `python3 run_quality.py --check` exits
non-zero when a cell is below its floor. Tables land in `quality/results/`.

```bash
cd sim
python3 -m venv .venv && .venv/bin/pip install -r requirements-quality.txt
bash quality/setup_lyra.sh
.venv/bin/python run_quality.py
```
